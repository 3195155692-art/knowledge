# 生信分析环境与工作流基础

> **一句话定位**：这一篇解决"动手之前要做对的事"——环境怎么装、文件怎么放、格式怎么认、结果怎么才能复现。
> **经验之谈**：生信分析 80% 的失败不是分析思路错，而是**环境混乱、版本不对、路径搞错、格式不匹配**。把这一篇的规范落实，后面的分析会顺很多。

---

## 一、先想清楚：算力放在哪里

| 方案 | 适用 | 优点 | 限制 |
| --- | --- | --- | --- |
| 本地电脑（Mac/Windows + Linux 子系统） | 学习、少量样本、芯片数据、单细胞小数据 | 零成本、随时可用 | 内存与磁盘有限，跑不动 WGS 比对 |
| 云服务器（包月/按量） | RNA-seq 常规分析、单细胞 | 弹性、可配置大内存 | 需自己维护环境，按小时计费 |
| 集群 / HPC（学校或医院平台） | 大队列、WGS、多样本并行 | 资源大、可排队跑 | 需要写作业脚本，学习成本 |
| 云平台（托管式流程） | 不想碰命令行 | 开箱即用 | 灵活性差、长期成本高、细节不透明 |

### 资源估算（按人类数据、单样本粗略估计）

| 任务 | 内存 | 磁盘（每样本） | 时间量级 |
| --- | --- | --- | --- |
| 芯片数据处理 | 2–8 GB | 数十 MB | 分钟级 |
| Bulk RNA-seq 定量（Salmon/kallisto） | 8–16 GB | 2–5 GB | 十几分钟 |
| Bulk RNA-seq 比对（STAR，人类） | **≥32 GB**（建索引更高） | 5–15 GB | 30–60 分钟 |
| 单细胞（1 万个细胞，Cell Ranger） | 32–64 GB | 20–50 GB | 数小时 |
| 全外显子 | 32–64 GB | 10–30 GB | 数小时 |
| 全基因组 | ≥64 GB | 50–150 GB | 十几小时 |

**结论**：做 RNA-seq 至少准备 **32 GB 内存 + 1 TB 存储**，做单细胞建议 64 GB。

## 二、环境与包管理（一次装对，长期省心）

### 2.1 三套生态各管一段

| 生态 | 管什么 | 安装方式 | 说明 |
| --- | --- | --- | --- |
| **conda / mamba（bioconda）** | 命令行生信工具（fastp、STAR、samtools、salmon…） | `conda install -c bioconda 工具名` | 生物信息工具的事实标准分发渠道 |
| **R + Bioconductor** | 统计与组学分析（DESeq2、limma、clusterProfiler…） | `BiocManager::install("包名")` | 组学统计的绝对主力 |
| **Python + 单细胞生态** | scanpy、scvi-tools、部分流程 | `pip`/`conda` | 单细胞与机器学习侧常用 |

### 2.2 版本固定的三条实操建议

1. **每个项目建独立环境**，不要把所有包装进 base：

```bash
conda create -n rnaseq -c conda-forge -c bioconda fastp fastqc star samtools subread salmon multiqc
conda activate rnaseq
conda env export > envs/rnaseq_$(date +%Y%m%d).yaml   # 存档，写进论文方法
```

2. **R 侧记录版本**：`R --version`、`packageVersion("DESeq2")`，并在脚本末尾 `sessionInfo()` 存档；
3. **不用最新的，用验证过的版本**：分析中途升级包版本是最常见的"结果突然不一致"原因。

### 2.3 进阶：容器与工作流引擎

| 工具 | 作用 | 什么时候需要 |
| --- | --- | --- |
| Docker / Singularity | 把环境打包成镜像，彻底解决"别人跑不出来" | 方法学论文、跨平台协作 |
| Nextflow / Snakemake | 把多个步骤串成可断点续跑的工作流 | 多样本、多步骤流程（如 nf-core 系列） |
| nf-core | 社区维护的现成流程（RNA-seq、WGS、ATAC 等） | 想做标准化流程又不想自己搭 |

**建议路径**：先用命令行手动跑通一遍理解每一步，再改用 Nextflow/Snakemake 做批量。

## 三、日常工作台

| 工具 | 用途 |
| --- | --- |
| RStudio | R 分析、画图（推荐与项目目录（`.Rproj`）配合使用） |
| VS Code + Remote SSH | 连服务器写代码，支持的插件生态好 |
| Jupyter / JupyterLab | Python 与交互式记录 |
| tmux / screen | 断开 SSH 后任务继续运行（**必学**） |
| nohup | 简易后台运行 |
| Git / GitHub | 版本管理，避免"改坏了回不去" |

### 3.1 集群（SLURM）最常用的几个命令

```bash
sinfo                 # 看有哪些队列和节点
squeue -u $USER       # 看自己的任务状态
sbatch run.sh         # 提交作业
scancel <作业号>       # 终止作业
sacct -u $USER        # 查看历史作业的资源使用（用于估算下次要多少内存）
```

**服务器使用礼貌准则**：不要在登录节点跑计算；不要一次提交几十个作业占满队列；跑完及时清理大文件。

### 3.2 长任务的标准姿势

```bash
tmux new -s rnaseq          # 新建会话
# ... 在会话里运行任务 ...
# Ctrl+B 然后 D 退出会话（任务继续跑）
tmux attach -t rnaseq       # 下次登录后回到会话
```

## 四、数据格式速查

| 格式 | 内容 | 常用命令/工具 |
| --- | --- | --- |
| FASTA | 序列（无质量值） | `grep -c ">" ref.fa` 数序列条数 |
| FASTQ | 测序 reads + 质量值 | `fastqc`、`fastp`、`seqkit stats` |
| SAM / BAM / CRAM | 比对结果 | `samtools view/sort/index/flagstat` |
| VCF / BCF | 变异 | `bcftools view/stats`、`tabix` |
| BED / GTF / GFF | 区间与注释 | `bedtools intersect`、`gtf2bed` |
| 表达矩阵 | 基因 × 样本 | `read.delim()`、`tximport` |
| 10x 三件套 | barcodes + features + matrix | `Read10X()`（Seurat） |
| h5ad / rds | 单细胞对象 | Scanpy / Seurat |
| bigWig / bedGraph | 覆盖度轨迹 | IGV、deepTools |

### 常用命令骨架

```bash
# 看文件前几行/压缩文件的头
head -n 4 sample.fq.gz | zcat 2>/dev/null || zcat sample.fq.gz | head -n 4

# 统计 FASTQ 的 reads 数与碱基数
seqkit stats -a sample.fq.gz

# BAM 统计比对率
samtools flagstat sample.sorted.bam | head

# 取目标区域
bedtools intersect -a regions.bed -b peaks.bed -wa > overlap.bed

# 快速查看大表头与列名
head -n 1 expr_matrix.tsv | tr '\t' '\n' | head -20
```

## 五、项目目录与文件命名规范

```
project_x/
├── 00_raw/            # 原始数据（只读，永不修改）
├── 01_meta/           # 样品表、临床信息、分组表
├── 02_ref/            # 参考基因组与注释
├── 03_clean/          # 质控后数据
├── 04_aligned/        # 比对结果
├── 05_quant/          # 定量结果
├── 06_results/        # 差异分析、富集、模型结果
├── 07_figures/        # 出图（含脚本）
├── scripts/           # 所有脚本，按步骤编号 01_xxx.sh
├── envs/              # 环境文件（yaml / renv.lock）
├── logs/              # 运行日志
└── README.md          # 数据来源、参数、运行顺序、版本
```

**三条铁律**

1. **原始数据只读**，任何处理都输出到新目录；
2. **不带空格和中文的文件名**（避免各种工具的编码报错），用下划线分隔；
3. **样品名在样品表、文件名、脚本中必须完全一致**——大小写、连字符、下划线都算不同。

### 样品表怎么写

| sample_id | fq1 | fq2 | group | batch | sex | age | stage |
| --- | --- | --- | --- | --- | --- | --- | --- |
| S1 | S1_R1.fq.gz | S1_R2.fq.gz | Tumor | 1 | M | 58 | II |
| S2 | S2_R1.fq.gz | S2_R2.fq.gz | Normal | 2 | F | 61 | II |

要点：**分组与批次必须同时列出**，这样在建模时才能发现混杂；临床列名用英文，值用统一编码，避免"阳性/positive/+"混用。

## 六、复现性：半年后你自己还能跑出来吗

| 做法 | 作用 |
| --- | --- |
| 一切操作写进脚本（不用一次性交互命令） | 可重跑、可追溯 |
| 脚本按 `01_`、`02_` 编号 | 明确运行顺序 |
| 记录软件与包版本（`sessionInfo()`、`conda env export`） | 论文方法部分可写，结果可复现 |
| 固定随机种子（`set.seed()`） | 聚类、抽样结果一致 |
| 参考文献基因组版本（如 GRCh38 + GENCODE v44） | 版本不一致 = 结果不可比 |
| Git 管理代码 | 改动可回溯 |
| README 写清数据来源与参数 | 他人（或未来的你）能接手 |
| 日志重定向（`> logs/xx.log 2>&1`） | 出错可查因 |

**投稿加分项**：把分析脚本与参数表作为补充材料提交，或在 GitHub 公开——这是审稿人越来越看重的部分。

## 七、三个"一错就全废"的关键点

1. **参考基因组与注释版本必须配套且全程一致。**
   比对用 GRCh38，注释就不能用 hg19 的 GTF；同一课题内不要中途换版本。报告里要写明：参考基因组版本 + 注释来源与版本号。
2. **链特异性参数必须与建库方式匹配。**
   RNA-seq 的 featureCounts/htseq 需要设置链特异性（`-s 0/1/2`）；设错会让计数大幅偏低甚至完全错乱。先用 RSeQC 的 `infer_experiment.py` 判断实际链特异性，再设置参数。
3. **坐标系统不能混用（0-based 半开 vs 1-based 闭区间）。**
   BED 是 0-based、GTF/VCF 是 1-based；混用时区域会偏一位，导致"首尾对不上"的诡异结果。用 `bedtools` 转换要显式说明。

## 八、常见报错与排查

| 现象 | 常见原因 | 排查方向 |
| --- | --- | --- |
| `Killed` / `Out of memory` | 内存不足 | 查看 `sacct` 或 `dmesg`，减少线程/分块处理/换大内存机器 |
| `No space left on device` | 磁盘满 | `df -h`、`du -sh *` 定位大文件，清理中间文件 |
| 包安装冲突（R/Python） | 依赖版本不兼容 | 建独立环境；优先 BiocManager/conda 安装 |
| `command not found` | 环境未激活 / PATH 问题 | `which 工具名`、`conda activate` |
| 文件读入报错、列数不齐 | 分隔符、BOM、换行符（CRLF）、中文编码 | 用 `file` 与十六进制工具（如 xxd）检查；统一为 UTF-8 与 LF |
| 结果全为 0 或异常少 | 链特异性设错、参考版本不匹配、样品名拼写不一致 | 检查参数与样品表 |
| 脚本突然报错但昨天能跑 | 包被升级 / 环境被改动 | 用固定环境文件重建，恢复版本 |
| 权限被拒 | 文件权限或目录配额 | `ls -l`、联系平台管理员 |
| 中文路径报错 | 工具不支持非 ASCII 路径 | 项目路径全部用英文 |

**通用排查顺序**：看日志末尾报错 → 确认输入文件是否存在且非空 → 确认样本名与参数 → 确认版本 → 换小数据复现。
